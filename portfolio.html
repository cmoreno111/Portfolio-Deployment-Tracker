The Problem

Deployments fail silently
when there's no single source of truth.

Operations teams managing multi-site deployments are drowning in emails, spreadsheets, and Slack threads. The information exists — it's just scattered everywhere.

Before — The Old Way
📋

Status lives in spreadsheets

Manual updates, stale data, no one sure which version is current. Every status meeting starts with "what's the latest on..."

🚧

Blockers go unnoticed

A deployment has been stuck for days but nobody flagged it. Leadership finds out weeks later. Escalations happen too late.

📨

Context gets lost in email

Notes, decisions, and site-specific details buried in inboxes. No institutional memory. New team members start from scratch.

After — DeployTrack
✦

One URL for the whole team

Everyone sees the same live data. Status updates propagate instantly. No more "which spreadsheet is current?"

🚩

Blockers are impossible to miss

Blocked deployments are flagged in the overview, in the table, and in the weekly report — with time in status and reason attached.

🗂️

Context is attached to the asset

Engineer notes and CS notes live alongside each deployment. Full history, timestamped, searchable. No institutional knowledge lost.

How It Was Built

Weekend project.
Production outcome.

No dev team, no budget, no runway. Just a problem worth solving and enough persistence to ship something real.

1
Define the problem

No single view of deployment status. Teams asking the same questions every day. Decided to build instead of complain.

2
Design the data model

Google Sheets as the database. Two tabs: deployments and history. Columns mapped to every field the team needed.

3
Build & ship the API

Apps Script web app handling GET requests. All reads and writes routed through a single endpoint. Deployed in hours.

4
Iterate with the team

Shipped the table first. Added notes, history, site overview, weekly report, and smart refresh over multiple weekends.
