The Context

The information existed.
It just lived everywhere.

When the rollout was handed to me, every site was at a different stage — different mounting, different camera models, different sampling progress. The data to run it was scattered across emails, spreadsheets, and Slack, and every status meeting started with "what's the latest on…"

What I walked into
📋

Status lives in spreadsheets

Manual updates and stale data. No one was sure which version was current.

🚧

Blockers go unnoticed

A deployment could sit stuck for days without anyone flagging it. By the time leadership heard, the escalation was already late.

📨

Context gets lost in email

Notes, decisions, and site-specific details were buried in inboxes. Anyone new to the account had to start from scratch.

What changed after I shipped DeployTrack
✦

One link for the whole team

Everyone saw the same live data. Updates reached the whole team right away, with no more asking which spreadsheet was current.

🚩

Blockers became hard to miss

Blocked deployments were flagged in the overview, the table, and the weekly report, showing how long they had been stuck and why.

🗂️

Context stayed with the asset

Engineer notes and customer success notes lived alongside each deployment, with a full timestamped history.

What I Built

Every feature came
from a real request.

I shipped the table first, then added each feature when the team hit a specific pain point in standups, customer calls, or leadership reviews.

01
📊
Live Status Dashboard

Every deployment, site, and status in one table, filterable by location, status, type, or owner. This replaced the spreadsheets.

Solved: "which version is current?"
02
🗺️
Site Overview

Card grid per location showing deployment counts by status. Blocked sites flagged prominently. Click any card to drill in instantly.

Solved: site-by-site status calls
03
📝
Dual Note System

Engineer notes and customer-facing notes side by side, with full history per deployment. A note is prompted on every status change.

Solved: context lost in email
04
⚡
Recent Updates Feed

The 50 most recently updated deployments with their latest notes inline, one click from the full record. Built for our daily syncs.

Solved: slow daily standups
05
📋
Auto Weekly Report

A leadership report that builds itself from live data: in progress, completed, blocked, completion stats, and next actions.

Solved: manual weekly report prep
06
🔧
Reliability Tuning

Instant saves, refresh only when the tab is visible, and automatic history archiving, so it stayed fast and needed no upkeep as usage grew.

Solved: slowdowns under real use
Key Decisions

The choices behind it,
and why I made them.

I had no dev team, no budget, and no time for a procurement cycle. Those constraints shaped every design choice.

01
Google Sheets as the database

The team already worked in Sheets, so the data stayed readable and editable even outside the app.

Trade-offNot built for huge scale, but right for dozens of sites, and it needed no approvals to start.
02
One HTML file, no framework

No build step or dependencies. Anyone could host it, open it, or pick it up after me.

WhyA tool only lasts if someone other than its builder can maintain it.
03
Two separate note streams

Engineers and customer success needed to say different things to different audiences about the same deployment.

WhyCustomer updates stayed clean, and technical detail wasn't lost.
04
A read-only view for stakeholders

Leadership and wider teams got the same live views (overview, recent updates, weekly report) without edit access.

WhyMore visibility, without risking accidental changes to the source of truth.

How I Built It

Weekend project.
Production outcome.

I used generative AI as my coding partner. I owned the rest: defining the problem, designing the data model, deciding what to build next, testing with the team, and rolling it out.

1
Define the problem

No single view of deployment status, and the team asking the same questions every day. I decided to build the fix instead of adding another spreadsheet.

2
Design the data model

Google Sheets as the database. Two tabs: deployments and history. Columns mapped to every field the team needed.

3
Build & ship the API

Apps Script web app handling GET requests. All reads and writes routed through a single endpoint. Deployed in hours.

4
Iterate with the team

Shipped the table first. Added notes, history, site overview, weekly report, and smart refresh over multiple weekends.
